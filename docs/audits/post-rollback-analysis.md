# Отчет о глубоком анализе архитектуры: Grand Strategy

## 1. Обзор архитектуры
Проект представляет собой ядро глобальной стратегии (Grand Strategy) в стиле игр Paradox Interactive (Hearts of Iron 4, Europa Universalis IV), разработанное на **Godot 4.x**. Архитектура разделена на оффлайн-пайплайн (генерация данных) и рантайм-отрисовку.

### 1.1. Система рендеринга карты
* **Растрово-векторный гибрид:** Для подложки используются растровые карты (`map_political.png`, `map_flat.png`), но рендеринг улучшен кастомным шейдером `SmoothPixel.gdshader` (сабпиксельное сглаживание пиксель-арта без размытия).
* **Система LOD для границ:** Скрипт `VectorMap.gd` разбивает векторные линии границ на чанки (512x512) и назначает их отдельным `Node2D`. Это позволяет движку автоматически отсекать (culling) невидимые границы за пределами экрана, что критически важно для производительности в стратегиях. 
* **Управление масштабированием:** Масштаб контролирует `MapPresentationController.gd`, который плавно переключает карту между режимами "Провинции/Штаты" (States) и "Страны" (Countries) на основе `overview_ratio` (соотношение экрана к размеру карты HOI4 - 5632.0).

### 1.2. Система взаимодействия (Picking)
* Взаимодействие с картой реализовано классическим для жанра способом — через цветовое кодирование. 
* В `Main.gd` загружается `state_id.png`, где каждый пиксель кодирует ID провинции в RGB (R + G<<8 + B<<16). Клик мыши считывает цвет пикселя и сопоставляет его с JSON-данными.
* Реализован умный "Fallback" алгоритм: если игрок кликает на границу, скрипт проверяет соседние пиксели (в радиусе 4px) и делает геометрическую сверку `Geometry2D.is_point_in_polygon`, чтобы избежать промахов.

### 1.3. Оффлайн-Пайплайн (Python)
Судя по списку файлов, в проекте присутствует мощный оффлайн-пайплайн:
* Скрипты `vectorize.py`, `build_states.py`, `build_countries.py` извлекают данные о границах и регионах из исходных Bitmap-карт (province_id.png, map_base.png).
* Данные сериализуются в оптимизированные JSON-файлы (`state_lines.json`, `states.json`), которые в рантайме быстро загружаются в память.

## 2. Сильные стороны (Pro-Level)
* **Асинхронная загрузка и кэширование линий:** Векторные данные предрасчитаны для 3 уровней детализации (LOD0, LOD1, LOD2). Линии перерисовываются (`queue_redraw`) только при изменении LOD или завершении зума.
* **Независимость UI от логики:** UI-элементы вынесены в `GameHUD.tscn` и `TopBar.tscn`. Выделение на карте плавно интегрируется с UI через сигналы (HUD реагирует на `show_state` / `show_country_sidebar`).
* **Модульность:** Шейдеры (вода, пиксели, границы) логически отделены от GDScript-логики, что упростит их дальнейшее расширение.

## 3. Уязвимости и точки роста (Технический долг)
* **Блокирующий парсинг JSON:** В `Main.gd::_ready()` происходит массивная загрузка и парсинг объемных словарей JSON (`states.json`, `state_lines.json`). По мере роста карты это вызовет длительный "фриз" при запуске игры. *Решение:* Перенести парсинг JSON в фоновый поток (Thread) или использовать бинарный формат ресурсов Godot (.tres/.res).
* **Просадки FPS при Redraw:** В `VectorMap.gd` при изменении LOD вызывается `queue_redraw()` для всех видимых чанков одновременно. Если чанков много, это может вызвать микрофриз (Spike).
* **Жесткое кодирование логики:** В `Main.gd` (строки 62-81) захардкожены проверки координат для "FRA_METRO" и "ENG_COLONY". *Решение:* Эти метаданные должны генерироваться оффлайн-пайплайном Python и храниться напрямую в `states.json`, чтобы убрать хардкод из движка.

## 4. Рекомендации по дальнейшему рефакторингу
1. **Переход на бинарные форматы:** Конвертировать выходные JSON из Python-скриптов в бинарные `.res` или PackedByteArray для мгновенной загрузки.
2. **Многопоточный поиск по ID:** Поиск ближайших пикселей `state_id.png` (радиус 4) можно со временем оптимизировать через шейдер вычисления ближайшего ID (Jump Flooding Algorithm).
3. **Оптимизация памяти лукапов:** Изображение `country_lookup_image` создается размером 16384x1. Для стратегии с тысячами провинций это работает отлично, но текстуру стоит обновлять фрагментарно (Texture2D.update), а не полностью перезаписывать при изменении владельца.
